# GREEN 결과 검수

승인된 RED 테스트를 기준으로 GREEN 구현을 검수한다. 목표는 **승인된 테스트를 보존하고, 범위 안에서, 계약을 실제로 만족하도록 구현했는지** 증거로 판정하는 것이다. 구현 주체는 같은 세션의 에이전트, 사람, 다른 에이전트 누구여도 된다. 보고가 있더라도 그대로 믿지 않고 직접 확인한다.

이 스킬은 별도 검수 절차가 필요할 때 선택한다. 같은 세션에서 구현과 검증을 끝내려면 `readable-tests`의 GREEN 안전장치를 따르면 된다. 이 스킬을 생략해도 구현 결과 검증은 생략할 수 없으며, 같은 에이전트의 자체 검증을 독립 검수로 표현하지 않는다.

검수 중에는 코드를 수정하지 않는다. 사용자가 수정을 요청한 경우에만 고치고, 그때도 승인된 테스트는 건드리지 않는다.

작업 전에 공통 정책(`../../references/tdd-policy.md`)을 읽고 따른다. 승인된 테스트 보존과 실행·보고 규칙이 검수 기준의 바탕이다. 마지막의 수정 요청은 다른 사람이나 에이전트에게 전달해도 이해할 수 있도록 공통 정책을 참조하지 말고 필요한 규칙을 직접 쓴다.

## 입력 확인

다음 필수 정보를 대화와 저장소에서 확보한다. 찾을 수 없으면 사용자에게 묻거나 부족한 증거로 표시한다.

- 작업 지시: 대화에서 승인된 요구사항과 범위 또는 `green-handoff` 지시문 등. 별도 위임 문서는 필수가 아니다.
- 승인된 테스트 파일 경로와 관련 테스트 전용 fixture/helper/setup 파일 경로
- 테스트 비교 기준: RED 커밋 해시 또는 파일별 `git hash-object` 값
- 작업 전 기준선: 테스트의 실패·통과 수와 검증 명령
- 이번 작업에 필요한 검증 명령: 대상 테스트, 전체 테스트, 타입 검사, lint 등 저장소 지침과 작업 지시에서 확인한 명령

구현자의 작업 보고는 있을 때만 확보한다. 같은 세션에서 구현했다는 이유로 위임 지시문이나 별도 보고를 새로 만들도록 요구하지 않는다.

비교 기준이 없으면 "승인된 테스트가 바뀌지 않았다"고 단정하지 않는다. 확인할 수 있는 범위(예: 현재 diff, 세션 기록)만 보고하고 한계를 적는다. 필수 증거가 없으면 검수 가능한 부분은 확인하되, 문제가 발견되지 않았다는 이유로 승인 가능이라고 하지 않는다.

## 검수 절차

### 1. 승인된 테스트 보존 (차단 항목)

- 비교 기준과 현재 테스트 파일을 비교한다. RED 커밋이 있으면 `git diff <RED 커밋> -- <테스트 경로>`, 없으면 `git hash-object <path>`를 기록된 값과 비교한다.
- 승인된 파일 밖에서도 테스트를 약화했는지 찾는다.
  - 새로 추가된 `skip`, `only`, `todo`, 예상 실패 표시
  - 테스트 설정(test setup), 전역 mock, 테스트 러너 설정, snapshot 변경
  - 테스트가 import하는 테스트 전용 fixture/helper 변경
- 변경이 있으면 사람의 승인 근거와 갱신된 비교 기준을 확인한다. 무승인 변경이 확인되면 다른 결과와 관계없이 판정은 **차단**이다. 무엇이 어떻게 바뀌었는지 diff로 보여 준다.
- 승인 여부나 보존 여부를 확인할 증거가 부족하면 확인한 변경과 미확인 항목을 나누어 보고하고, 이를 승인된 변경으로 간주하지 않는다.

### 2. 변경 범위

- `git status`와 diff로 변경된 파일 전체를 확인한다. 추적되지 않는 새 파일도 포함한다.
- 작업 지시에서 승인된 구현 범위와 대조해 범위 밖 변경을 찾는다.
  - 관련 없는 리팩터링, 포맷만 바뀐 파일
  - 의존성·lockfile·빌드/lint 설정 변경
  - 작업 지시와 공통 정책의 금지 사항을 어긴 변경(커밋, push 포함)
- 범위 밖 변경이 정당해 보여도 승인 대상으로 표시하고, 판단은 사람에게 맡긴다.

### 3. 검증 재실행

- 입력 확인에서 확보한 필수 검증 명령을 직접 실행한다. 위임 지시문이 없으면 저장소 지침과 승인된 작업 지시에서 확인한다.
- 결과를 기준선과 비교한다.
  - 승인된 RED 테스트가 모두 통과하는가?
  - 원래 통과하던 테스트 중 새로 실패하는 것이 있는가?
  - 새로 생긴 타입·lint 오류가 있는가? 원래 있던 오류와 구분한다.
- 실행하지 못한 명령은 이유와 함께 적는다. 받은 보고의 결과로 대신하지 않는다. 환경 오류로 assertion까지 실행하지 못한 경우를 계약 불충족으로 인한 테스트 실패와 구분한다.

### 4. 구현 리뷰

- 테스트를 통과시키기만 하는 구현이 아닌지 확인한다.
  - 테스트에 쓰인 특정 값·ID·문구를 분기 조건으로 쓰는 코드
  - 테스트 환경을 감지해 다르게 동작하는 코드
  - mock 경계를 우회해 결과만 맞추는 코드
- 작업 지시의 확정 정책 중 테스트로 검증하지 않는 부분이 구현되었는지 확인한다.
- 계약 밖 판단이 승인된 기준과 맞는지 확인한다. 판단 근거가 대화나 보고에 없으면 사람이 확인할 항목으로 남긴다.
- 저장소 관례(에러 처리, 로깅, API 모듈 구조 등)를 따랐는지 본다. 단순 취향 차이는 지적하지 않는다.

### 5. 보고 대조

- 구현자의 보고가 있으면 실제 결과와 비교한다. 변경 파일 목록, 실행 결과 수치, 계약 밖 판단, 남은 TODO를 확인한다.
- 보고와 실제가 다르면 차이를 그대로 적는다.
- 별도 보고가 없으면 이 항목은 해당 없음으로 표시한다. 보고가 없는 것만으로 검증 불충분으로 판정하지 않으며, 테스트 보존·실행 결과 등의 필수 증거는 직접 확인한다.

## 판정

- **차단**: 승인된 테스트나 관련 테스트 설정 등의 무승인 변경이 확인됐다. 또는 승인된 테스트가 계약 불충족으로 실패한다.
- **수정 필요**: 회귀, 범위 밖 변경, 테스트 통과만 노린 구현, 확정 정책 누락, 새 타입·lint 오류 등 수정할 문제가 확인됐다.
- **검증 불충분**: 위 문제가 확인되지는 않았지만, 테스트 비교 기준 부재, 필수 검증 미실행, 환경 오류 등으로 필요한 증거가 부족하다. 부족한 증거, 확인하지 못한 항목, 확보 방법을 적는다.
- **승인 가능**: 필수 증거를 확보했고 위 문제가 없다. 사람이 결정할 항목은 따로 나열한다.

차단 → 수정 필요 → 검증 불충분 → 승인 가능 순으로 판정한다. 확인된 문제가 있으면 증거 부족으로 가리지 말고 해당 판정을 내리되, 확인하지 못한 항목도 함께 보고한다. "문제를 발견하지 못함"과 "확인하지 못함"을 구분하며, 필수 증거가 없으면 승인 가능으로 판정하지 않는다.

## 보고 형식

1. 판정과 한 줄 요약
2. 항목별 결과: 테스트 보존, 변경 범위, 검증 재실행(실제 명령과 수치), 구현 리뷰, 보고 대조(보고가 없으면 해당 없음). 근거로 파일 경로와 줄 번호를 든다. 자체 검증인지 독립 검수인지도 구분한다.
3. 사람이 결정할 항목과 부족한 증거: 확인하지 못한 내용, 이유, 필요한 추가 증거와 확보 방법
4. 수정 요청: 판정이 차단이나 수정 필요일 때, 구현 담당자에게 그대로 전달할 수 있는 코드 블록. 수정 범위, 지킬 가드레일, 다시 실행할 검증 명령을 포함한다. 검증 불충분이면 결함 수정을 단정하지 않고 증거 확보에 필요한 다음 행동을 적는다.
