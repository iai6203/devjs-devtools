# GREEN 결과 검수

다른 에이전트가 끝낸 GREEN 구현을 승인된 RED 테스트 기준으로 검수한다. 목표는 **테스트를 바꾸지 않고, 범위 안에서, 계약을 실제로 만족하도록 구현했는지** 증거로 판정하는 것이다. 받은 보고를 그대로 믿지 않고 직접 확인한다.

검수 중에는 코드를 수정하지 않는다. 사용자가 수정을 요청한 경우에만 고치고, 그때도 승인된 테스트는 건드리지 않는다.

## 입력 확인

다음을 확보한다. 없는 항목은 저장소에서 찾고, 찾을 수 없으면 사용자에게 묻는다.

- 위임 지시문: `green-handoff`로 작성한 지시문 또는 그에 준하는 작업 지시
- 승인된 테스트 파일 경로
- 테스트 비교 기준: RED 커밋 해시 또는 파일별 `git hash-object` 값
- 작업 전 기준선: 전체 테스트의 실패·통과 수
- 받는 에이전트의 작업 보고

비교 기준이 없으면 "승인된 테스트가 바뀌지 않았다"고 단정하지 않는다. 확인할 수 있는 범위(예: 현재 diff, 세션 기록)만 보고하고 한계를 적는다.

## 검수 절차

### 1. 승인된 테스트 보존 (차단 항목)

- 비교 기준과 현재 테스트 파일을 비교한다. RED 커밋이 있으면 `git diff <RED 커밋> -- <테스트 경로>`, 없으면 `git hash-object <path>`를 기록된 값과 비교한다.
- 승인된 파일 밖에서도 테스트를 약화했는지 찾는다.
  - 새로 추가된 `skip`, `only`, `todo`, 예상 실패 표시
  - 테스트 설정(test setup), 전역 mock, 테스트 러너 설정, snapshot 변경
  - 테스트가 import하는 테스트 전용 fixture/helper 변경
- 하나라도 바뀌었다면 다른 결과와 관계없이 판정은 **차단**이다. 무엇이 어떻게 바뀌었는지 diff로 보여 준다.

### 2. 변경 범위

- `git status`와 diff로 변경된 파일 전체를 확인한다. 추적되지 않는 새 파일도 포함한다.
- 지시문의 구현 범위와 대조해 범위 밖 변경을 찾는다.
  - 관련 없는 리팩터링, 포맷만 바뀐 파일
  - 의존성·lockfile·빌드/lint 설정 변경
  - 지시문의 "하지 말 것"을 어긴 변경(커밋, push 포함)
- 범위 밖 변경이 정당해 보여도 승인 대상으로 표시하고, 판단은 사람에게 맡긴다.

### 3. 검증 재실행

- 지시문의 검증 명령을 직접 실행한다. 대상 테스트, 전체 테스트, 타입 검사, lint를 포함한다.
- 결과를 기준선과 비교한다.
  - 승인된 RED 테스트가 모두 통과하는가?
  - 원래 통과하던 테스트 중 새로 실패하는 것이 있는가?
  - 새로 생긴 타입·lint 오류가 있는가? 원래 있던 오류와 구분한다.
- 실행하지 못한 명령은 실행하지 못했다고 적는다. 받은 보고의 결과로 대신하지 않는다.

### 4. 구현 리뷰

- 테스트를 통과시키기만 하는 구현이 아닌지 확인한다.
  - 테스트에 쓰인 특정 값·ID·문구를 분기 조건으로 쓰는 코드
  - 테스트 환경을 감지해 다르게 동작하는 코드
  - mock 경계를 우회해 결과만 맞추는 코드
- 지시문에 적힌 확정 정책 중 테스트로 검증하지 않는 부분이 구현되었는지 확인한다.
- 계약 밖 판단이 지시문의 제안 기준과 맞는지, 보고에 적혀 있는지 확인한다.
- 저장소 관례(에러 처리, 로깅, API 모듈 구조 등)를 따랐는지 본다. 단순 취향 차이는 지적하지 않는다.

### 5. 보고 대조

- 받는 에이전트의 보고와 실제 결과를 비교한다. 변경 파일 목록, 실행 결과 수치, 계약 밖 판단, 남은 TODO를 확인한다.
- 보고와 실제가 다르면 차이를 그대로 적는다.

## 판정

- **차단**: 승인된 테스트나 테스트 설정이 바뀌었다. 또는 승인된 테스트가 실패한다.
- **수정 필요**: 승인된 테스트는 통과한다. 다만 회귀, 범위 밖 변경, 테스트 통과만 노린 구현, 확정 정책 누락, 새 타입·lint 오류 중 하나가 있다.
- **승인 가능**: 위 문제가 없다. 사람이 결정할 항목(계약 밖 판단, 정당해 보이는 범위 밖 변경)은 따로 나열한다.

## 보고 형식

1. 판정과 한 줄 요약
2. 항목별 결과: 테스트 보존, 변경 범위, 검증 재실행(실제 명령과 수치), 구현 리뷰, 보고 대조. 근거로 파일 경로와 줄 번호를 든다.
3. 사람이 결정할 항목
4. 수정 요청: 판정이 차단이나 수정 필요일 때, 받는 에이전트에게 그대로 다시 보낼 수 있는 코드 블록. 수정 범위, 지킬 가드레일, 다시 실행할 검증 명령을 포함한다.
