# 읽을 수 있는 테스트 명세

테스트 파일 자체를 사람이 승인할 수 있는 실행 명세로 작성한다. 검수자가 별도 설명 문서나 복잡한 헬퍼를 따라가지 않고 **기대 동작 → 준비 상황 → 행동 → 검증 근거**를 읽을 수 있게 한다.

작업 전에 공통 정책(`../../references/tdd-policy.md`)을 읽고 따른다. 단계 흐름, 승인된 테스트 보존, 미확정 정책 질문, 식별자 병기, 실행·보고 규칙은 그 문서에 있다.

## 작업 시작

1. 저장소 지침, 요구사항, 대상 테스트와 주변 테스트, 테스트 실행 명령을 먼저 확인한다.
2. 사용자가 요청한 범위와 단계(RED, GREEN, REFACTOR, 가독성 개선, 리뷰)를 따른다. 이 스킬을 사용한다는 이유만으로 제품 코드를 수정하거나 GREEN으로 넘어가지 않는다.
3. 요구사항에서 확정되지 않은 정책이나 기대 동작은 공통 정책에 따라 질문한다. `test-list`로 승인된 테스트 목록이 있으면 그 사례를 RED 범위로 삼는다.
4. 기존 테스트 프레임워크와 프로젝트 관례를 활용한다. 이 형식을 도입하려고 프레임워크를 추가하거나 관련 없는 테스트까지 일괄 변환하지 않는다.

## 테스트 파일의 구성

- `describe` 또는 동등한 그룹에는 기능과 조건을 적는다. 불필요하게 깊게 중첩하지 않는다.
- `it` / `test` 또는 동등한 테스트 이름에는 조건과 기대 동작을 드러낸다. 언어와 형식은 사용자 요청, 언어·프레임워크 제약, 저장소 관례에 맞춘다. 문장형 이름이 어려우면 유효한 식별자를 사용하고 주석으로 보완한다.
- 이름이 한국어가 아니라면 해당 테스트 가까이에 조건과 기대 동작을 한국어로 설명하는 주석을 반드시 둔다. 한국어 이름으로 계약이 드러나면 필요한 맥락만 주석으로 보충한다.
- 본문에서 준비·행동·검증이 구분되게 한다. 빈 줄, `Given` / `When` / `Then`, AAA 등 구분 형식은 저장소 관례와 테스트 길이에 맞게 선택한다. 주석에는 기술 동작의 번역보다 도메인 상황과 의도를 쓴다.
- 코드만으로 알기 어려운 정책과 이유는 해당 테스트 가까이에 짧은 주석으로 둔다. 요구사항 식별자가 있다면 함께 남길 수 있다.
- 별도 시나리오 표나 문서를 기본 산출물로 만들지 않는다. 요청받아 작성할 때는 실제 테스트 위치에 연결하고, 테스트 파일만으로도 이해할 수 있게 한다.

## 설명과 코드 식별자 연결

- 테스트 이름, 주석, 정책 설명에서 변수·함수를 설명할 때는 공통 정책에 따라 실제 식별자를 반드시 괄호로 병기한다. 예: `허용 한도(maxBytes)`. 테스트 이름의 언어나 주석 구분 형식을 바꿔도 이 규칙은 생략하지 않는다.
- 식별자는 해당 테스트 코드와 정확히 일치시킨다. 이름을 바꾸면 테스트 이름과 주석의 괄호 표기도 함께 갱신한다.

## 본문과 검증의 규칙

아래 Given / When / Then은 설명을 위한 구분이며, 같은 형식의 주석을 강제하지 않는다.

### Given: 상황이 드러나야 한다

- 기대 결과를 이해하는 데 중요한 입력, 경계값, 상태, 권한, 서버 응답은 본문에서 보이게 한다.
- 반복적인 기술 설정과 중요하지 않은 기본 데이터만 fixture나 헬퍼로 분리한다.
- 공유 설정에 시나리오별 핵심 조건을 숨기지 않는다. 각 테스트는 실행 순서와 다른 테스트의 상태에 의존하지 않아야 한다.
- mock은 외부 경계 등 필요한 곳에 한정한다. 검증 대상 자체나 그 결과를 mock하여 테스트가 스스로 정답을 만들어내지 않게 한다.

### When: 계약의 행동이 드러나야 한다

- 핵심 행동이 무엇인지 명확하게 표현한다. UI 테스트는 사용자 상호작용, API나 함수 테스트는 공개된 인터페이스 호출을 중심으로 쓴다.
- 비동기 동작을 적절히 기다린다. 임의의 sleep이나 실제 외부 서비스 상태에 기대지 않는다.

### Then: 설명한 계약을 실제로 증명해야 한다

- 한 테스트는 하나의 동작 계약을 검증한다. 그 계약을 증명하는 데 필요하다면 여러 assertion을 사용한다.
- 테스트 이름과 한국어 설명에 약속한 결과를 빠짐없이 검증한다. 버튼 활성화만 확인했다면 실제 재시도 요청까지 성공한다고 이름이나 설명에 쓰지 않는다.
- 내부 상태, private 메서드, 불필요한 호출 순서보다 관찰 가능한 결과를 검증한다. 요청 전송 자체가 계약이면 경계에서 요청 내용과 횟수를 검증할 수 있다.
- 중요한 기대값과 assertion은 본문에 둔다. `expectEverythingWorks()` 같은 헬퍼나 큰 snapshot으로 핵심 계약을 숨기지 않는다.
- 실제 값에서 기대값을 다시 계산하거나 제품 로직을 복제해 같은 버그를 공유하지 않는다.
- 매개변수화 테스트는 각 사례의 조건과 기대값, 실패한 사례의 이름을 쉽게 읽을 수 있을 때 사용한다.
- 가독성 개선 작업에서는 기존 검증 범위와 강도를 보존한다. assertion 삭제나 기대값 완화를 리팩터링으로 취급하지 않는다.

## 구조 예시

아래는 한국어 이름과 GWT 주석을 선택한 예시다. 함수와 헬퍼는 가상이며, 실제 저장소의 API와 확정된 정책으로 대체한다. 이 예시의 정책을 요구사항으로 간주하지 않는다.

```ts
describe('파일 검증(validateFile)', () => {
  describe('파일(file) 크기가 허용 한도(maxBytes)를 초과한 경우', () => {
    it('파일(file)을 거부하고 허용 한도(maxBytes)를 알려준다', () => {
      // Given: 허용 한도(maxBytes)보다 1바이트 큰 파일(file)이다.
      const maxBytes = 1024;
      const file = createFile({ size: 1025 });

      // When: 파일(file)을 검증한다(validateFile).
      const result = validateFile(file, { maxBytes });

      // Then: 검증 결과(result)에 거부 여부(accepted), 초과 사유(reason), 허용 한도(maxBytes)를 담는다.
      expect(result).toEqual({
        accepted: false,
        reason: 'size-exceeded',
        maxBytes: 1024,
      });
    });
  });
});
```

한국어 이름을 쓰지 않는 저장소에서는 다음처럼 가까운 주석으로 계약을 설명할 수 있다. 이 예시는 기대값이 중요한 본문에 드러나므로 GWT 주석을 반복하지 않는다.

```ts
// 파일(file) 크기가 허용 한도(maxBytes)를 초과한 상황이다.
// 파일 검증(validateFile)은 파일(file)을 거부하고 허용 한도(maxBytes)를 알려준다.
it('rejects oversized files(file) and reports the limit(maxBytes)', () => {
  const maxBytes = 1024;
  const file = createFile({ size: 1025 });

  const result = validateFile(file, { maxBytes });

  expect(result).toEqual({
    accepted: false,
    reason: 'size-exceeded',
    maxBytes: 1024,
  });
});
```

## TDD 단계별 안전장치

### RED

- 제품 코드를 수정하지 않는다. 기능 구현이나 임시 구현을 추가해 GREEN으로 만들지 않는다.
- 테스트와 필요한 테스트 전용 fixture/helper 범위에서 작업한다. 그 밖의 설정·의존성 변경이 필요하면 먼저 승인을 요청한다.
- 대상 테스트를 실행하고 실패 이유를 확인한다. 기능 미구현으로 인한 기대 결과 불충족과 환경·mock·문법 오류를 구분한다.
- 새 공개 API가 아직 없어 import/type 단계에서 실패한다면, 이를 명시하고 assertion까지 실행된 RED처럼 보고하지 않는다.
- 실패를 강제하는 assertion, skip, todo, 예상 실패 표시로 정상적인 RED 검증을 대체하지 않는다.
- 이미 통과하는 테스트를 억지로 실패시키지 않는다. 기존에 만족된 동작인지, 검증이 약한지 확인하고 결과를 보고한다.
- 변경 모드 목록으로 진행할 때는 변경 유형에 따라 다룬다. 기존 테스트 수정은 공통 정책의 "기존 테스트 변경"을 따른다.
  - `변경`: 목록에 적힌 기존 테스트의 기대값을 이후 값으로 고친다. 고친 테스트는 실패해야 한다. 이전 기대값과 이후 기대값을 RED 보고에 적는다.
  - `폐기`: 목록에 적힌 기존 테스트만 삭제하고 삭제한 테스트를 RED 보고에 적는다.
  - `공백`(특성화): 현재 동작을 고정하는 테스트라서 현재 코드에서 통과해야 한다. RED 실패로 보고하지 않고, 주석에 현재 동작 기록임을 밝힌다.
  - `유지`: 기존 테스트를 고치지 않는다. 보강이 승인된 경우에만 assertion을 더한다.
- 변경 모드의 RED 보고에서는 기존 테스트의 diff를 승인된 목록 항목과 대조해 보여 준다. 목록에 없는 기존 테스트 변경이 diff에 있으면 안 된다.
- 실행하지 못했거나 원인을 확인하지 못했다면 RED 검증 완료라고 하지 않는다.
- RED만 요청받았다면 검수 가능한 상태에서 멈추고 GREEN은 별도 승인을 기다린다.
- 승인 후 같은 세션에서 GREEN을 구현할 수 있다. 다른 에이전트·세션으로 넘길 때만 `green-handoff`를 선택한다. 별도 결과 검수가 필요하면 구현 주체와 관계없이 `green-review`를 사용할 수 있다.

### GREEN

- 사람이 승인한 RED 테스트와 요청된 구현 범위를 확인한다. 같은 세션에서 진행할 때는 위임 지시문이나 다른 에이전트의 작업 보고를 요구하지 않는다.
- 구현 전에 승인된 테스트와 관련 테스트 전용 파일의 비교 기준(기존 RED 커밋 해시 또는 파일별 `git hash-object` 값), 작업 전 실행 결과를 기록한다. 기준을 남기기 위해 임의로 커밋하지 않는다.
- 사람이 승인한 테스트는 동작 계약이다. 통과시키기 위해 테스트를 수정·비활성화하거나 검증을 약화하지 않는다. 세부 규칙은 공통 정책의 "승인된 테스트는 동작 계약이다"를 따른다.
- 구현 후 비교 기준과 대조해 테스트 보존을 확인하고, 변경이 요청 범위 안에 있는지 검토한다.
- 대상 테스트와 관련 회귀 테스트, 저장소 지침이나 작업 지시에서 요구한 타입 검사·lint 등을 직접 실행하고 실제 실행한 범위만 보고한다. 별도 검수 스킬을 쓰지 않아도 이 검증은 생략하지 않는다.
- 비교 기준이나 필수 실행 결과가 없으면 검증 완료라고 하지 않는다. 발견한 문제와 확인하지 못한 항목을 구분하고, 부족한 증거와 확보 방법을 보고한다.

### REFACTOR (필요 시)

- GREEN 이후 요청·승인된 범위 안에서만 구조를 개선한다. 리팩터링을 이유로 기능을 추가하거나 동작 계약을 바꾸지 않는다.
- 승인된 테스트를 보존하고 대상 테스트와 관련 회귀 검사 등을 다시 실행한다. 같은 에이전트의 자체 검증을 독립 검수로 표현하지 않는다.

## 마무리 검수 및 보고

변경한 각 테스트에 대해 다음을 확인한다.

- 테스트 이름과 가까운 한국어 설명으로 조건과 기대 동작을 이해할 수 있는가? 한국어가 아닌 이름에는 한국어 주석이 있는가?
- 본문에 중요한 입력과 기대값이 보이는가?
- 준비·행동·검증이 구분되며, 작성한 주석이 실제 코드와 일치하는가?
- 설명하는 변수·함수의 실제 식별자를 괄호로 병기했고, 해당 테스트 코드의 이름과 정확히 일치하는가?
- assertion이 테스트 이름과 한국어 설명의 계약을 증명하며, 다른 결과라면 실패하는가?
- 필요한 정상·실패·경계 사례 중 빠진 것이 있는가? 요구사항상 불명확한 사례는 질문으로 남겼는가?
- 가독성을 높이는 과정에서 검증을 약화하지 않았는가?

최종 보고는 변경한 테스트 경로, 핵심 계약, 실행 명령과 결과, 미확정 사항을 짧게 정리한다. RED에서는 실패한 테스트별 원인과 의도한 실패인지도 보고하되, 테스트 본문을 설명하는 별도 장문 명세로 대체하지 않는다.
