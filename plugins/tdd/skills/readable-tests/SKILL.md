# 읽을 수 있는 테스트 명세

테스트 파일 자체를 사람이 승인할 수 있는 실행 명세로 작성한다. 검수자가 별도 설명 문서나 복잡한 헬퍼를 따라가지 않고 **기대 동작 → 준비 상황 → 행동 → 검증 근거**를 읽을 수 있게 한다.

## 작업 시작

1. 저장소 지침, 요구사항, 대상 테스트와 주변 테스트, 테스트 실행 명령을 먼저 확인한다.
2. 사용자가 요청한 범위와 단계(RED, GREEN, 가독성 개선, 리뷰)를 따른다. 이 스킬을 사용한다는 이유만으로 제품 코드를 수정하거나 GREEN으로 넘어가지 않는다.
3. 요구사항에서 확정되지 않은 정책이나 기대 동작은 질문한다. 현재 구현을 그대로 정답으로 삼거나 오류 문구, 제한값 등을 임의로 확정하지 않는다.
4. 기존 테스트 프레임워크와 프로젝트 관례를 활용한다. 이 형식을 도입하려고 프레임워크를 추가하거나 관련 없는 테스트까지 일괄 변환하지 않는다.

## 테스트 파일의 구성

- `describe` 또는 동등한 그룹에는 기능과 조건을 적는다. 불필요하게 깊게 중첩하지 않는다.
- `it` / `test` 또는 동등한 테스트 이름에는 승인할 기대 동작을 문장으로 적는다. 예: `업로드 요청이 실패하면 오류를 표시하고 업로드 버튼을 다시 활성화한다`.
- 본문은 빈 줄과 `Given`, `When`, `Then` 주석으로 구분한다. 주석에는 기술 동작의 번역보다 도메인 상황과 의도를 쓴다.
- 테스트 이름과 설명은 별도 언어 지침이 없으면 한국어로 작성한다. 언어상 식별자 제약이 있으면 유효한 식별자와 한국어 설명을 함께 사용한다.
- 코드만으로 알기 어려운 정책과 이유는 해당 테스트 가까이에 짧은 주석으로 둔다. 요구사항 식별자가 있다면 함께 남길 수 있다.
- 별도 시나리오 표나 문서를 기본 산출물로 만들지 않는다. 요청받아 작성할 때는 실제 테스트 위치에 연결하고, 테스트 파일만으로도 이해할 수 있게 한다.
- RED 실행 결과, 임시 실패 로그, 작업 진행 상태는 테스트 주석에 남기지 않고 작업 보고에 둔다.

## 설명과 코드 식별자 연결

- 테스트 이름, Given / When / Then 주석, 정책 설명, 작업 보고에서 코드의 변수나 함수를 설명할 때는 자연어 설명 바로 뒤에 실제 식별자를 괄호로 병기한다. 예: `허용 한도(maxBytes)`, `파일(file)`, `파일을 검증한다(validateFile)`.
- 도메인 의미와 의도를 먼저 쓰고 식별자는 코드 위치를 찾는 단서로 사용한다. 식별자만 나열하거나 코드 한 줄을 그대로 번역하지 않는다.
- 설명에 등장하는 대상에 대응하는 식별자만 적는다. 코드와 무관한 설명에 억지로 괄호를 붙이거나, 존재하지 않는 이름 또는 설명용 별칭을 만들지 않는다.
- 식별자는 해당 테스트 코드와 정확히 일치시킨다. 이름을 바꾸면 테스트 이름과 주석, 관련 설명의 괄호 표기도 함께 갱신한다.

## 본문과 검증의 규칙

### Given: 상황이 드러나야 한다

- 기대 결과를 이해하는 데 중요한 입력, 경계값, 상태, 권한, 서버 응답은 본문에서 보이게 한다.
- 반복적인 기술 설정과 중요하지 않은 기본 데이터만 fixture나 헬퍼로 분리한다.
- 공유 설정에 시나리오별 핵심 조건을 숨기지 않는다. 각 테스트는 실행 순서와 다른 테스트의 상태에 의존하지 않아야 한다.
- mock은 외부 경계 등 필요한 곳에 한정한다. 검증 대상 자체나 그 결과를 mock하여 테스트가 스스로 정답을 만들어내지 않게 한다.

### When: 계약의 행동이 드러나야 한다

- 핵심 행동이 무엇인지 명확하게 표현한다. UI 테스트는 사용자 상호작용, API나 함수 테스트는 공개된 인터페이스 호출을 중심으로 쓴다.
- 비동기 동작을 적절히 기다린다. 임의의 sleep이나 실제 외부 서비스 상태에 기대지 않는다.

### Then: 제목을 실제로 증명해야 한다

- 한 테스트는 하나의 동작 계약을 검증한다. 그 계약을 증명하는 데 필요하다면 여러 assertion을 사용한다.
- 제목에 약속한 결과를 빠짐없이 검증한다. 버튼 활성화만 확인했다면 실제 재시도 요청까지 성공한다고 제목에 쓰지 않는다.
- 내부 상태, private 메서드, 불필요한 호출 순서보다 관찰 가능한 결과를 검증한다. 요청 전송 자체가 계약이면 경계에서 요청 내용과 횟수를 검증할 수 있다.
- 중요한 기대값과 assertion은 본문에 둔다. `expectEverythingWorks()` 같은 헬퍼나 큰 snapshot으로 핵심 계약을 숨기지 않는다.
- 실제 값에서 기대값을 다시 계산하거나 제품 로직을 복제해 같은 버그를 공유하지 않는다.
- 매개변수화 테스트는 각 사례의 조건과 기대값, 실패한 사례의 이름을 쉽게 읽을 수 있을 때 사용한다.
- 가독성 개선 작업에서는 기존 검증 범위와 강도를 보존한다. assertion 삭제나 기대값 완화를 리팩터링으로 취급하지 않는다.

## 구조 예시

아래는 형식 설명용 예시다. 함수와 헬퍼는 가상이며, 실제 저장소의 API와 확정된 정책으로 대체한다. 이 예시의 정책을 요구사항으로 간주하지 않는다.

```ts
describe('파일 검증(validateFile)', () => {
  describe('파일(file) 크기가 허용 한도(maxBytes)를 초과한 경우', () => {
    it('파일(file)을 거부하고 허용 한도(maxBytes)를 알려준다', () => {
      // Given: 허용 한도(maxBytes)보다 1바이트 큰 파일(file)이다.
      const maxBytes = 1024;
      const file = createFile({ size: 1025 });

      // When: 파일(file)을 검증한다(validateFile).
      const result = validateFile(file, { maxBytes });

      // Then: 검증 결과(result)에 거부 여부(accepted), 초과 사유(reason), 허용 한도(maxBytes)를 담는다.
      expect(result).toEqual({
        accepted: false,
        reason: 'size-exceeded',
        maxBytes: 1024,
      });
    });
  });
});
```

## TDD 단계별 안전장치

### RED

- 제품 코드를 수정하지 않는다. 기능 구현이나 임시 구현을 추가해 GREEN으로 만들지 않는다.
- 테스트와 필요한 테스트 전용 fixture/helper 범위에서 작업한다. 그 밖의 설정·의존성 변경이 필요하면 먼저 승인을 요청한다.
- 대상 테스트를 실행하고 실패 이유를 확인한다. 기능 미구현으로 인한 기대 결과 불충족과 환경·mock·문법 오류를 구분한다.
- 새 공개 API가 아직 없어 import/type 단계에서 실패한다면, 이를 명시하고 assertion까지 실행된 RED처럼 보고하지 않는다.
- 실패를 강제하는 assertion, skip, todo, 예상 실패 표시로 정상적인 RED 검증을 대체하지 않는다.
- 이미 통과하는 테스트를 억지로 실패시키지 않는다. 기존에 만족된 동작인지, 검증이 약한지 확인하고 결과를 보고한다.
- 실행하지 못했거나 원인을 확인하지 못했다면 RED 검증 완료라고 하지 않는다.
- RED만 요청받았다면 검수 가능한 상태에서 멈추고 GREEN은 별도 승인을 기다린다.

### GREEN 및 이후 리팩터링

- 사람이 승인한 테스트는 동작 계약으로 취급한다.
- 통과시키기 위해 테스트를 삭제·비활성화하거나 기대값·검증 강도를 완화하지 않는다.
- 승인된 테스트 자체의 수정이 필요하면 이유와 계약에 미치는 영향을 설명하고 먼저 승인받는다.
- 대상 테스트와 관련 회귀 테스트를 실행하고, 실제 실행한 범위만 보고한다.

## 마무리 검수 및 보고

변경한 각 테스트에 대해 다음을 확인한다.

- 제목만 읽어도 조건과 기대 동작을 이해할 수 있는가?
- 본문에 중요한 입력과 기대값이 보이는가?
- Given / When / Then과 실제 코드가 일치하는가?
- 설명하는 변수·함수의 실제 식별자를 괄호로 병기했고, 해당 테스트 코드의 이름과 정확히 일치하는가?
- assertion이 제목을 증명하며, 다른 결과라면 실패하는가?
- 필요한 정상·실패·경계 사례 중 빠진 것이 있는가? 요구사항상 불명확한 사례는 질문으로 남겼는가?
- 가독성을 높이는 과정에서 검증을 약화하지 않았는가?

최종 보고는 변경한 테스트 경로, 핵심 계약, 실행 명령과 결과, 미확정 사항을 짧게 정리한다. RED에서는 실패한 테스트별 원인과 의도한 실패인지도 보고하되, 테스트 본문을 설명하는 별도 장문 명세로 대체하지 않는다.
