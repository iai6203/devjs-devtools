# GREEN 위임 지시문 작성

사람이 승인한 RED 테스트를 바탕으로, 다른 코딩 에이전트·세션이 GREEN 구현을 끝낼 수 있는 지시문을 작성한다. 지시문을 받는 에이전트는 이 대화의 맥락을 모른다고 가정하고, **지시문 하나만 읽고 작업과 검증까지 마칠 수 있게** 쓴다.

이 스킬은 작업을 전달할 때 사용하는 선택 사항이다. 같은 세션에서 GREEN을 구현한다면 지시문을 만들 필요 없이 `readable-tests`의 GREEN 안전장치를 따른다.

이 스킬은 지시문만 작성한다. 제품 코드나 테스트를 수정하지 않고 GREEN 구현도 시작하지 않는다.

작업 전에 공통 정책(`../../references/tdd-policy.md`)을 읽고 따른다. 단, 받는 에이전트는 그 문서를 읽을 수 없다고 가정한다. 지시문에서 공통 정책을 참조하지 말고, 필요한 규칙(특히 아래 템플릿의 가드레일)을 지시문 안에 직접 쓴다.

## 전제 확인

1. RED 테스트가 사람에게 승인되었는지 확인한다. 승인 여부가 불분명하면 묻는다. 승인되지 않은 테스트를 계약으로 넘기지 않는다.
2. 승인된 테스트 파일 경로를 확정한다. 같은 작업에서 바뀐 테스트 전용 fixture/helper/setup 파일도 함께 포함한다.
3. 승인된 테스트가 커밋되어 있지 않으면, 검수할 때 변경 여부를 비교할 기준이 필요하다. 다음 중 하나를 사용자에게 제안한다.
   - RED 테스트를 먼저 커밋한다. 검수에서는 그 커밋과 비교한다.
   - 커밋하지 않을 경우, 각 테스트 파일의 `git hash-object <path>` 값을 지시문의 검수 기준에 기록한다.

## 수집할 내용

공통 정책에 따라 저장소와 대화에서 확인한 사실만 쓰고, 확인하지 못한 내용은 미확정으로 표시한다.

- **맥락**: 이 작업이 필요한 이유. 예: 외부 API·백엔드 변경, 요구사항, 이슈. 받는 에이전트가 계약의 의도를 이해하는 데 필요한 만큼만 쓴다.
- **작업 위치**: 저장소 절대 경로, 브랜치, worktree 여부, 패키지 루트.
- **테스트 계약**: 테스트 파일별 핵심 계약. 테스트 이름과 기대값(문구, 요청 경로, 상태 코드 등)을 요약한다. 테스트 본문을 통째로 옮기지 않고 경로를 함께 적는다.
- **기존 테스트 변경**: 유지보수 작업에서 RED 단계에 승인을 받고 고치거나 삭제한 기존 테스트, 그리고 이전 기대값과 이후 기대값. 받는 에이전트가 이 변경을 의도된 계약으로 이해하고, 그 밖의 기존 테스트가 실패하면 회귀로 다루게 하기 위해서다. 해당 없으면 생략한다.
- **경계에서 검증하는 형식**: 테스트가 mock 경계에서 검증하는 형식은 정확히 적는다. 예: 요청 경로, 호출 인자, 모듈 경로. 받는 에이전트가 다른 형식으로 구현해 테스트와 어긋나는 일을 막기 위해서다.
- **구현 위치**: 수정이 필요한 제품 코드 파일과 함수. 직접 열어 확인한 뒤 적는다.
- **확정된 정책**: 대화에서 사람이 확정한 정책과 문구. 테스트로 검증하지 않는 부분도 확정된 것이면 포함한다. 예: 다른 유형에 같은 규칙 적용.
- **계약 밖 판단**: 테스트도 확정된 정책도 다루지 않아 받는 에이전트가 판단해야 하는 부분. 판단 기준을 제안하되 계약처럼 쓰지 않는다. 판단 결과는 보고하게 한다.
- **범위 밖**: 이번에 하지 않을 일. 예: 목록 재조회, 다른 화면 연동. 남겨 둘 TODO가 있으면 명시한다.
- **검증 명령**: 저장소 스크립트(`package.json`, `Makefile`, `pyproject.toml` 등)에서 확인한 실제 명령. 대상 테스트, 전체 테스트, 타입 검사, lint를 포함한다.
- **기준선**: 지시문을 쓰는 시점에 전체 테스트를 직접 실행한 결과. 실패 수와 통과 수를 적고, 실패하는 테스트가 승인된 RED뿐인지 확인한다. 실행하지 못했다면 그렇다고 적는다.

## 지시문 작성 원칙

- 경로는 절대 경로나 저장소 기준 경로로 쓴다. "앞서 말한", "위 대화" 같은 표현을 쓰지 않는다.
- 사용자에게 보이는 문구, 상태 코드, 요청 경로 같은 기대값은 테스트와 글자 하나까지 같게 쓴다.
- 구현 방법은 테스트 계약과 저장소 관례를 지키는 데 필요한 만큼만 지정한다. 세부 설계는 받는 에이전트에게 맡긴다.
- 가드레일(아래 템플릿의 "승인된 테스트"와 "하지 말 것")은 생략하거나 약화하지 않는다.
- 커밋·push 여부는 사용자의 지시를 따른다. 지시가 없으면 "커밋하지 않는다"로 쓴다.
- 저장소 지침 파일(`AGENTS.md`, `CLAUDE.md` 등)에 작업 전 확인 사항이 있으면 지시문에 포함한다.

## 지시문 템플릿

섹션 순서와 제목을 유지한다. 해당 내용이 없는 섹션은 "없음"으로 남긴다.

````markdown
# 작업: <작업 이름> GREEN 구현

## 작업 위치와 맥락
- 작업 디렉터리: <절대 경로> (<브랜치>, <worktree 여부>)
- <이 작업이 필요한 이유와 외부 변경 요약>
- TDD로 진행 중이다. RED 테스트는 사람이 승인했다. 지금 할 일은 GREEN이다.

## 승인된 테스트 (동작 계약)
- `<테스트 파일 경로>`: <핵심 계약 한 줄>

**테스트 파일은 수정하지 마라.** 삭제, skip, only, 기대값 완화, assertion 제거, 테스트 전용 설정 변경도 금지다. 테스트 자체를 고쳐야 한다고 판단되면 구현을 멈추고, 이유와 계약에 미치는 영향을 보고해 승인을 받아라.

## 승인된 기존 테스트 변경 (해당 시)
- `<테스트 경로>` › <테스트 이름>: <이전 기대값> → <이후 기대값> (또는 삭제)

위 변경은 RED 단계에서 이미 승인되어 반영되었다. 이 밖의 기존 테스트가 실패하면 회귀다. 테스트를 고치지 말고 구현을 고치거나, 멈추고 보고해라.

## 구현할 내용
### 1. <기능 단위>
- <구현 위치>
- <테스트가 경계에서 검증하는 형식과 기대값>
- <확정된 정책>

## 계약 밖 판단
- <판단할 부분>: <제안 기준>. 어떻게 처리했는지 보고에 적어라.

## 하지 말 것
- 범위 밖의 리팩터링, 의존성 추가, 설정 변경을 하지 않는다.
- <범위 밖 작업과 남겨 둘 TODO>
- <커밋·push 정책>

## 검증
<패키지 루트>에서 아래를 실행한다.
1. `<대상 테스트 명령>`: 승인된 테스트 <N>개가 모두 통과해야 한다.
2. `<전체 테스트 명령>`: 전체 테스트가 통과해야 한다. 작업 전 기준은 <기준선>이다.
3. `<타입 검사·lint 명령>`: 새 오류가 없어야 한다.

## 검수 기준
- 승인된 테스트 기준: <RED 커밋 해시> 또는 파일별 `git hash-object` 값
- 이 값과 달라진 테스트 파일이 있으면 승인 근거와 갱신된 기준을 확인한다. 무승인 변경은 검수에서 차단된다.
- 비교 기준이나 필수 검증 결과가 없으면 검증 완료라고 하지 말고, 부족한 증거와 확보 방법을 보고한다.

## 보고 형식
- 변경한 파일과 각 파일의 핵심 변경 내용
- 실제로 실행한 명령과 결과(통과/실패 수)
- 계약 밖 판단 내용과 남은 TODO
- 하지 못한 일이나 막힌 부분
````

## 출력

- 지시문은 그대로 복사해 붙여 넣을 수 있게 하나의 코드 블록으로 출력한다. 지시문 안에 코드 블록이 있으면 바깥 펜스를 더 길게 쓴다(```` 등).
- 사용자가 파일로 요청하면 지정한 경로에 저장한다. 저장소 안에 저장할 때는 커밋 대상이 되지 않도록 위치를 확인한다.
- 지시문 뒤에 짧게 덧붙인다.
  - 미확정 사항: 사람이 정해야 하지만 아직 정하지 않은 부분
  - 검수 방법: 구현 후 검증은 필수이며, 별도 검수 절차가 필요하면 `green-review` 스킬을 선택할 수 있다
