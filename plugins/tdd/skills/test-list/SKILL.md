# 테스트 목록 합의

요구사항을 테스트 코드로 옮기기 전에 **검증할 동작 계약의 목록**을 만들고 사람의 승인을 받는다. 승인된 목록은 RED 테스트의 범위가 된다. 그러면 RED 검토에서는 "이 사례가 맞는가"를 다시 논의하지 않고 "테스트 코드가 이 사례를 제대로 표현했는가"에 집중할 수 있다.

이 스킬은 목록만 만든다. 테스트 코드나 제품 코드를 작성·수정하지 않는다.

작업 전에 공통 정책(`../../references/tdd-policy.md`)을 읽고 따른다. 미확정 정책 질문, 식별자 병기, 단계 흐름 규칙은 그 문서에 있다.

## 작업 시작

1. 요구사항의 출처를 확인한다. 예: 대화, 이슈, 기획 문서, API 명세. 출처가 여러 개면 서로 어긋나는 부분을 찾는다.
2. 저장소에서 다음을 확인한다.
   - 대상 기능의 공개 인터페이스와 외부 경계(API, 저장소, UI 이벤트 등)
   - 대상 기능과 주변 기능의 기존 테스트, 테스트 프레임워크와 관례
   - 저장소 지침 파일(`AGENTS.md`, `CLAUDE.md` 등)의 테스트 관련 규칙
3. 현재 구현은 사례를 찾는 단서로만 쓴다. 기대 동작은 공통 정책에 따라 요구사항과 사람의 결정으로 정한다.
4. 기존 동작을 바꾸거나 고치는 작업이면 아래 "변경 모드"로 진행한다. 예: 기존 기능의 정책 변경, 버그 수정, 기존 코드 위에 기능 확장.

## 사례 찾기

각 기능 단위에서 다음 관점으로 사례를 찾는다. 모든 관점을 억지로 채우지 않고, 요구사항과 관련 있는 것만 남긴다.

- **정상**: 요구사항이 약속한 주된 흐름
- **실패**: 잘못된 입력, 권한 없음, 외부 경계의 오류·타임아웃, 중복 요청
- **경계**: 한도 바로 아래·같음·바로 위, 빈 값, 0개·1개·여러 개, 최솟값·최댓값
- **상태**: 로딩 중, 이미 처리됨, 이전 작업 실패 후 재시도처럼 앞선 상태에 따라 결과가 달라지는 경우
- **회귀**: 이번 변경으로 깨지면 안 되는 기존 동작. 기존 테스트로 이미 보호되는지 확인한다.

사례 하나는 하나의 동작 계약이다. 한 사례에 결과가 둘 이상 섞여 있고 각각 따로 실패할 수 있으면 나눈다.

## 목록 작성 규칙

- `readable-tests`의 테스트 구성과 맞춘다. 기능과 조건은 묶음 제목(`describe` 또는 동등한 그룹)으로, 기대 동작은 사례 제목으로 쓴다. 승인된 계약을 테스트 이름과 가까운 한국어 설명으로 옮길 수 있게 하되, 사례 제목과 실제 테스트 이름의 언어·형식이 같을 필요는 없다. 한국어가 아닌 테스트 이름에는 계약을 설명하는 한국어 주석을 둔다.
- 사례 제목에는 조건과 관찰 가능한 결과를 함께 쓴다. 예: `업로드 요청이 실패하면 오류를 표시하고 업로드 버튼을 다시 활성화한다`.
- 기대값이 중요하면 사례 아래에 적는다. 예: 문구, 상태 코드, 요청 경로, 한도 값. 확정되지 않은 값은 지어내지 않고 미확정으로 표시한다.
- 코드의 변수나 함수는 공통 정책에 따라 실제 식별자를 괄호로 병기한다. 아직 없는 이름을 새로 제안할 때는 `(제안: validateFile)`처럼 제안임을 드러낸다.
- 각 사례에 근거를 단다.
  - **확정**: 요구사항이나 사람의 결정에 근거가 있다. 출처를 짧게 적는다.
  - **제안**: 요구사항에 없지만 필요해 보여 추가했다. 이유를 적는다.
  - **미확정**: 기대 동작을 정하려면 사람의 결정이 필요하다. 질문 목록에 연결한다.
- 기존 테스트가 이미 같은 계약을 검증하면 새 사례로 만들지 않고 해당 테스트 경로와 이름을 적는다. 기존 테스트가 약하면 보강 사례로 따로 표시한다.
- 테스트 방식이 중요하면 짧게 적는다. 예: 단위·통합·UI 테스트 구분, mock할 외부 경계. 세부 구현은 RED 단계에서 정한다.

## 변경 모드

유지보수에서는 새 사례를 찾는 것보다 **기존 계약 중 무엇이 유지되고, 바뀌고, 사라지는지**를 합의하는 것이 중요하다. 변경 모드에서는 위 규칙에 더해 다음을 따른다.

### 기존 테스트 파악

1. 변경 대상 기능을 검증하는 기존 테스트를 찾는다. 대상 기능을 직접 import하는 테스트, 같은 공개 인터페이스를 거치는 통합·UI 테스트, 관련 fixture/helper/snapshot을 포함한다.
2. 찾은 테스트가 검증하는 계약을 테스트 경로와 이름으로 정리한다. 테스트 이름만 보지 말고 assertion이 실제로 무엇을 확인하는지 읽는다.
3. 대상 테스트를 실행해 현재 상태를 기준선으로 남긴다. 이미 실패하거나 skip된 테스트가 있으면 따로 적는다. 실행하지 못했다면 그렇다고 적는다.
4. 변경 대상 동작 중 어떤 테스트도 검증하지 않는 부분을 찾는다.

### 변경 유형

각 사례에 정상·실패·경계·상태 관점과 함께 변경 유형을 하나 붙인다.

- **유지**: 이번 변경 후에도 그대로여야 하는 기존 계약이다. 이를 보호하는 기존 테스트의 경로와 이름을 적는다. 기존 테스트가 약하면 보강이 필요하다고 표시한다.
- **변경**: 기대 동작이 바뀌는 기존 계약이다. 이전 기대값과 이후 기대값, 수정할 기존 테스트의 경로와 이름을 적는다.
- **신규**: 기존에 없던 계약이다. 일반 목록의 사례와 같다.
- **폐기**: 더 이상 유효하지 않은 계약이다. 삭제할 기존 테스트와 폐기 근거를 적는다. 근거가 요구사항에 없으면 미확정으로 두고 질문한다.
- **공백**: 이번 변경이 영향을 줄 수 있지만 어떤 테스트도 보호하지 않는 기존 동작이다. 변경 전에 특성화 테스트로 현재 동작을 고정할지, 범위 밖으로 둘지 질문한다. 특성화 테스트로 고정할 때는 관찰한 현재 동작을 기대값으로 적고, 그 동작이 의도인지 함께 묻는다.

`변경`과 `폐기`는 사람이 기존 테스트 수정을 승인하는 항목이다. 승인 범위가 분명하도록 바뀌는 기대값과 테스트를 구체적으로 적는다. 이 목록에 없는 기존 테스트는 수정 대상이 아니다.

### 버그 수정

버그 수정은 작은 변경 모드로 다룬다.

- 버그를 재현하는 사례를 먼저 둔다. 기대 동작의 근거(요구사항, 이슈, 사람의 결정)를 적고, 현재 동작은 재현 결과로 적는다.
- 기존 테스트가 버그 동작을 기대값으로 고정하고 있다면 그 테스트를 `변경`으로 올린다.
- 같은 원인이 영향을 줄 수 있는 인접 동작을 `유지` 또는 `공백`으로 확인한다. 범위를 넓히지 않고 관련 있는 것만 남긴다.

## 진행 순서 제안

RED를 한 번에 모두 쓰지 않고 나눠 진행할 수 있도록 순서를 제안한다.

- 가장 단순하면서 공개 인터페이스의 모양을 정하는 사례를 먼저 둔다.
- 앞선 사례의 구현 위에 쌓이는 사례를 뒤에 둔다.
- 미확정 사례는 결정될 때까지 순서에서 뺀다.
- 변경 모드에서는 특성화 테스트로 고정하기로 한 `공백` 사례를 먼저 둔다. 동작을 바꾸기 전에 보호망을 만들기 위해서다. 그다음 `변경`·`폐기`, `신규` 순으로 둔다.

## 출력 형식

새 기능은 다음 형식을 쓴다.

````markdown
# 테스트 목록: <기능 이름>

## 요구사항 출처
- <출처와 요약>

## 사례
### <기능(식별자)> — <조건>
1. [정상·확정] <사례 제목>
   - 기대값: <문구, 상태 코드, 값 등>
   - 근거: <출처>
2. [경계·제안] <사례 제목>
   - 이유: <추가한 이유>
3. [실패·미확정] <사례 제목> → 질문 Q1

## 기존 테스트로 충족
- `<테스트 경로>` › <테스트 이름>: <대응하는 계약>

## 질문
- Q1. <결정할 내용> (선택지: <A> / <B>, 제안: <A와 이유>)

## 범위 밖
- <이번에 검증하지 않을 동작과 이유>

## 진행 순서 제안
1. 사례 1 → 2. 사례 2 → ...
````

변경 모드는 다음 형식을 쓴다. 사례 번호는 유형과 관계없이 이어서 매긴다.

````markdown
# 테스트 목록: <기능 이름> (변경)

## 요구사항 출처
- <변경 요청이나 버그 보고의 출처와 요약>

## 기존 테스트 기준선
- `<테스트 경로>`: <통과·실패·skip 수>, 실행 명령 `<명령>`
- <이미 실패하거나 skip된 테스트, 실행하지 못한 테스트>

## 사례
### <기능(식별자)> — <조건>
1. [정상·유지] <사례 제목>
   - 보호: `<테스트 경로>` › <테스트 이름>
2. [실패·변경·확정] <사례 제목>
   - 이전: <이전 기대값> → 이후: <이후 기대값>
   - 수정할 테스트: `<테스트 경로>` › <테스트 이름>
   - 근거: <출처>
3. [경계·신규·제안] <사례 제목>
   - 이유: <추가한 이유>
4. [정상·폐기·확정] <사례 제목>
   - 삭제할 테스트: `<테스트 경로>` › <테스트 이름>
   - 근거: <폐기 근거>
5. [상태·공백] <사례 제목> → 질문 Q1
   - 현재 동작: <관찰한 동작과 확인 방법>

## 질문
- Q1. <공백 사례를 특성화 테스트로 고정할지, 현재 동작이 의도인지> (선택지: <A> / <B>, 제안: <A와 이유>)

## 범위 밖
- <이번에 검증하지 않을 동작과 이유>

## 진행 순서 제안
1. 사례 5(특성화) → 2. 사례 2 → 3. 사례 4 → 4. 사례 3
````

## 승인 이후

- 목록을 출력한 뒤 멈추고 승인을 기다린다. 사람이 질문에 답하거나 사례를 고치면 목록을 갱신해 다시 보여 준다.
- 미확정 사례와 질문이 남아 있으면 승인 완료로 보지 않는다. 사람이 미확정인 채로 진행하라고 하면 해당 사례를 범위 밖으로 옮긴다.
- 사람이 목록을 파일로 남기길 원하면 지정한 경로에 저장한다. 기본 산출물은 대화 안의 목록이다.
- 승인된 목록으로 RED 테스트를 작성할 때는 `readable-tests`를 따른다. RED를 작성하면서 목록에 없는 사례가 필요해지면 임의로 추가하지 않고 목록 변경으로 다시 승인받는다.
- 변경 모드에서 `변경`·`폐기` 승인은 목록에 적힌 기존 테스트를 적힌 내용대로 고치는 것만 허용한다. 목록에 없는 기존 테스트를 고쳐야 하면 목록 변경으로 다시 승인받는다.
