# TDD 공통 정책

`tdd` 플러그인의 모든 스킬이 함께 따르는 정책이다. 각 스킬은 이 정책 위에 단계별 규칙을 더한다. 스킬 문서와 이 문서가 어긋나면 이 문서를 따르고, 어긋난 부분을 사용자에게 알린다.

## 단계 흐름과 승인 지점

| 단계 | 스킬 | 산출물 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- | --- |
| RED | `readable-tests` | 실패하는 테스트 | 사람이 RED 테스트를 승인한다 |
| GREEN 위임 | `green-handoff` | 위임 지시문 | 받는 에이전트가 구현을 끝낸다 |
| GREEN 검수 | `green-review` | 판정과 수정 요청 | 판정이 승인 가능이다 |

- 사람이 요청한 단계만 수행한다. 한 단계를 끝내면 멈추고 승인을 기다린다. 승인 없이 다음 단계로 넘어가지 않는다.
- 각 단계는 앞 단계의 승인된 산출물을 범위로 삼는다. 범위를 바꿔야 하면 앞 단계로 돌아가 다시 승인받는다.
- 모든 단계를 거칠 필요는 없다. 예를 들어 GREEN을 위임하지 않고 직접 구현할 수 있다.

## 승인된 테스트는 동작 계약이다

- 사람이 승인한 테스트를 삭제·비활성화하지 않는다. `skip`, `only`, `todo`, 예상 실패 표시를 추가하지 않는다.
- 기대값을 완화하거나 assertion을 제거하지 않는다. 테스트 전용 설정, 전역 mock, fixture/helper, snapshot을 바꿔 검증을 약화하지 않는다.
- 승인된 테스트를 고쳐야 한다고 판단되면 작업을 멈춘다. 이유와 계약에 미치는 영향을 설명하고 먼저 승인받는다.
- 가독성 개선이나 리팩터링을 이유로 검증 범위와 강도를 줄이지 않는다.

## 요구사항과 미확정 정책

- 기대 동작은 요구사항과 사람의 결정으로 정한다. 현재 구현의 동작을 정답으로 삼지 않는다.
- 확정되지 않은 정책, 오류 문구, 제한값 등은 임의로 확정하지 않고 질문한다. 질문할 때는 선택지와 제안을 함께 제시한다.
- 저장소와 대화에서 확인한 사실만 쓴다. 확인하지 못한 내용은 미확정으로 표시한다.

## 설명과 코드 식별자 연결

- 테스트 이름, 주석, 목록, 지시문, 작업 보고에서 코드의 변수나 함수를 설명할 때는 자연어 설명 바로 뒤에 실제 식별자를 괄호로 병기한다. 예: `허용 한도(maxBytes)`, `파일(file)`, `파일을 검증한다(validateFile)`.
- 도메인 의미와 의도를 먼저 쓰고 식별자는 코드 위치를 찾는 단서로 사용한다. 식별자만 나열하거나 코드 한 줄을 그대로 번역하지 않는다.
- 설명에 등장하는 대상에 대응하는 식별자만 적는다. 코드와 무관한 설명에 억지로 괄호를 붙이거나, 존재하지 않는 이름 또는 설명용 별칭을 만들지 않는다.
- 식별자는 실제 코드와 정확히 일치시킨다. 이름을 바꾸면 관련 설명의 괄호 표기도 함께 갱신한다.

## 작업 범위

- 저장소 지침 파일(`AGENTS.md`, `CLAUDE.md` 등), 기존 테스트 프레임워크, 프로젝트 관례를 먼저 확인하고 따른다.
- 단계에 필요한 범위 밖의 리팩터링, 의존성 추가, 빌드·테스트·lint 설정 변경을 하지 않는다. 필요하면 먼저 승인을 요청한다.
- 커밋과 push는 사용자의 지시가 있을 때만 한다.

## 실행과 보고

- 테스트, 타입 검사, lint는 저장소 스크립트에서 확인한 실제 명령으로 실행한다.
- 실제로 실행한 명령과 결과(통과·실패 수)만 보고한다. 실행하지 못했거나 원인을 확인하지 못했다면 그렇다고 적는다.
- 다른 에이전트나 이전 작업의 보고를 직접 확인한 결과로 대신하지 않는다.
- 진행 상태, 임시 로그, 실행 결과는 테스트 코드나 주석이 아니라 작업 보고에 둔다.

## 다른 에이전트에게 넘기는 문서

- 지시문처럼 다른 에이전트가 읽을 문서에서는 이 문서를 참조하지 않는다. 받는 에이전트가 이 문서를 읽을 수 있다고 가정하지 않고, 필요한 규칙을 문서 안에 직접 쓴다.
